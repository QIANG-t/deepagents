# 第二里程碑：真实数据只读预览

状态：已完成。以下是本阶段验收目标和实现范围；实测证据见[隔离联调记录](milestone2_integration_validation.md)。

## 用户路径

1. 用户在 InvenTree 采购页输入一个隔离测试生产单 ID，提交分析任务。
2. 插件用当前登录用户的权限读取生产单、物料需求和可核实的库存事实，保存任务归属及生产单 ID。
3. 页面显示每条需求行的原始数量、已消耗、已分配、待满足数量，以及对应 BuildLine 和 Part ID。
4. 对同一 Part 的多条需求行只展示一次共享库存。库存位置或其他分配影响不能可靠确定时，显示“待核实”和原因，不输出采购建议量。
5. 刷新页面或重启服务后，用户仍能查看自己的任务；其他用户不能读取该任务。

## 本阶段技术栈

| 层 | 技术 | 本阶段用途 |
| --- | --- | --- |
| 插件后端 | Python 3.11、Django、InvenTree AppMixin/UrlsMixin | 登录与业务权限检查、只读查询、任务持久化。 |
| 页面 | TypeScript、React、Mantine、Vite、InvenTree UserInterfaceMixin | 输入生产单 ID，展示原始数据、来源和待核实原因。 |
| 数据 | 隔离 InvenTree 实例、PostgreSQL | 使用显式生成的测试生产单和专用数据卷；不连接生产库。 |
| 算法与验证 | `Decimal`、单元测试、隔离实例 HTTP/浏览器检查 | 核对数量、同 Part 去重、拒绝越权访问和重启恢复。 |

Deep Agents 的模型调用、报价文档检索、MCP 和多 Agent 留在后续里程碑。本阶段先建立模型工具所依赖的可信数据来源。插件内不开放采购单写入。

## 通过条件

- 一个含至少两条物料需求的测试生产单可在页面完成任务创建和预览。
- 响应含 Build、BuildLine、Part 的可核对 ID；每个展示数量都能追溯到来源字段或明确标为假设。
- 同一 Part 出现在两条需求行时，库存不重复相加；库存语义不确定则显示待核实。
- 匿名、无所需业务权限、任务非所有者分别被拒绝；刷新及重启后任务仍可读取。
- 页面不提供审批、采购单创建或向供应商下单操作。

## 面试讲法

“先把真实数据读取和权限边界做通，让 Agent 后续调用工具时得到的是可追溯事实。生产单物料行可能重复引用同一物料，库存必须按物料去重；无法确认库存位置或其他分配时，我让系统停止给出精确采购量。”
