# 采购 Agent：面试讲解提纲

## 一分钟说明

“我以 InvenTree 的生产单采购为场景，在 Deep Agents 上做一个可审计的采购助手。原系统已经有采购向导，所以我没有把已有的缺口计算重新包装成 Agent。我的增量目标是跨生产单汇总、理解有来源的供应商报价、在证据不足时请求澄清，并在人工批准后生成待处理草稿。第一阶段选原生 InvenTree 插件：它让用户在采购页面查看任务，接口沿用系统登录态；采购写入暂时关闭。模型处理非结构化报价和工具选择，数量、换算、总价与审批版本由确定性代码计算。”

说完后按实际情况展示：[设计决策](architecture_decisions.zh-CN.md)、[隔离实例验证](integration_spike.md)、[测试案例](evaluation_plan.md)。演示前先核对这三份文件中的最新结果。

## 面试官常问的四个问题

| 问题 | 回答要点 |
| --- | --- |
| 为什么用 Agent？ | 原采购向导已经能算部分缺口。Agent 的候选价值是跨生产单查询、理解报价附件、指出来源冲突并向人澄清。需要和原向导、规则程序用同一批案例比较，不能预设 Agent 更好。 |
| 为什么先做原生插件？ | 采购人员在现有页面核对任务和权限。先验证 InvenTree 的 UI、URL、数据库扩展点；如果模型运行拖慢主服务，再拆出模型服务，但保留插件作为身份和审批入口。 |
| 怎样防止模型乱买？ | 模型没有批准权限；服务端绑定方案摘要与数据快照，写前重新读取，关键数量用 `Decimal` 计算。真实写入目前关闭，直到持久幂等和部分订单行恢复通过测试。 |
| 怎样证明项目有效？ | 记录现有采购向导、规则程序、Agent 三组的完成率、错误写入、人工介入、耗时和费用。当前只有合成案例及部分离线判定器，没有可用于简历的对比成绩。 |

## 如实说明边界

第一阶段插件只显示任务元数据。库存、供应商报价、模型调用、审批和真实采购单写入尚未形成端到端流程。面试时把“插件登录态与持久化已验证”和“Agent 采购能力待接入”分别说明；具体完成程度以[隔离实例验证](integration_spike.md)为准。
