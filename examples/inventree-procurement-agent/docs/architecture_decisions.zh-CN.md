# 采购 Agent 的设计决策

记录日期：2026-09-28。这里记录项目选择、代价和验证条件，供开发与面试复盘。文中“已决定”不代表功能已运行。

## ADR-1：先验证 InvenTree 原生插件（用户已选择）

**背景。** InvenTree 有 `UserInterfaceMixin`、`UrlsMixin` 等插件扩展点。采购向导已能生成建议量、选择供应商物料并添加采购单行。本项目需要在用户熟悉的界面内展示跨生产单的方案、来源和审批状态。[源码核查](preflight.md)与[接口契约](inventree_api_contract.md)列出证据。

**选择。** 先做一个只读插件：面板、登录后可访问的接口、可恢复的任务记录。通过运行验证后，再把本目录的 Deep Agents 工作流接入插件。若实测发现模型依赖、执行时间或资源占用不适合 InvenTree 进程，则将模型运行拆成独立服务；插件继续承担用户身份、权限和审批入口。

**取舍。** 原生插件使真实业务演示和权限归属更清楚，但 InvenTree 开发镜像、前端构建及插件安装的准备成本更高。独立服务较易启动模型，但必须额外解决登录态、接口授权与系统内入口。[第一阶段集成核查](integration_spike.md)证明插件安装和基本任务接口；[第二阶段联调](milestone2_integration_validation.md)证明真实 Build 数据读取、任务创建、权限拒绝、重启恢复和浏览器预览。模型仍待接入。

**通过条件。** 在隔离 InvenTree 实例里，登录用户能看到只读面板和任务；未登录用户被拒绝；无采购权限用户不能访问审批或写入动作；重启后任务仍在。保留实际请求、响应、日志和运行命令。没有这些证据时，插件仍是候选实现。

**面试讲法。** “我先验证系统原生扩展点，因为采购人员需要在现有界面核对数据和权限。我设置了一个最小插件验证门槛；如果模型运行与主服务冲突，再把模型计算拆出去，同时保留插件作为授权与审批入口。”

## ADR-2：模型负责理解，确定性代码负责关键数字

跨生产单缺口、库存去重、包装换算、报价总价和审批版本由可复算的程序处理。模型读取有来源的报价资料、选择查询工具、指出冲突或缺失并解释方案。当前 InvenTree 供应商字段没有可直接使用的交期和订货倍数，缺少来源时应向人澄清。[API 契约](inventree_api_contract.md)说明字段边界。

**面试讲法。** “让模型负责非结构化信息和下一步选择，数量与价格交给确定性函数。这样我能为每个采购数字给出数据来源，也能在报价缺失时停止。”

## ADR-3：审批后只创建待处理草稿

写入前应将审批绑定方案摘要与数据快照，重读库存和报价，验证权限、数量和供应商，写入后回查 `PENDING` 采购单及每条订单行。InvenTree 创建采购单与行项目是多个请求；持久幂等、网络结果未知和部分行恢复未完成前，真实 REST 适配器的写入保持关闭。当前原型仅用模拟网关测试了流程。

**面试讲法。** “我把模型输出当作建议，审批和写入由服务端控制。采购单创建涉及多个请求，因此必须先解决重复提交和部分成功恢复，再允许真实写入。”

## ADR-4：用现有产品和规则程序作基线

同一批案例比较 InvenTree 原采购向导、无模型规则程序和 Agent；分别记录任务是否完成、错误写入、人工介入、响应时间和费用。只把实际运行结果写入简历。当前已有 [18 个合成案例及评测方案](evaluation_plan.md)，离线判定器只支持其中 C01–C06；尚无三条基线的成绩。

**面试讲法。** “我把原系统和规则程序放进对照组，检查 Agent 在报价理解、澄清和审批执行上是否真的提供增量。”

## ADR-5：插件内读取 Build 上下文中的库存注解

**背景。** 同一个 Part 可出现在一张生产单的多条 BuildLine 中。隔离实例 BO-9001 有两行需求 4 和 6；生产单指定库位可用库存为 5。BuildLine 列表在传入 Build 上下文时，两行都会显示同一个库存值 5；若逐行相加就会错误地得到 10。单条 BuildLine 详情返回的全局库存 12 也不适合这张限定库位的生产单。[数据核查](real_data_fixture_validation.md)列出实际接口结果。

**选择。** 插件后端使用 InvenTree ORM 和 `BuildLineSerializer.annotate_queryset(..., build=selected_build)`，按 Part 汇总需求、每个 Part 只采用一次一致的库存注解。缺口 `max(未满足需求合计－可用库存, 0)` 只作为初步事实，附来源和警示。注解缺失、非法或多行冲突时，库存和缺口显示“待核实”。

**取舍。** 这样能复用宿主的库位与分配口径，且直接使用会话身份；代价是插件与所核查的 InvenTree 版本绑定。它尚未处理在途供应、替代料及可选或消耗性物料策略，因此 5 件缺口不能直接转成采购建议量。任务保存的是分析时快照，重启后可追溯，但不代表实时库存。

**权限边界。** API 用 InvenTree 的 `check_user_permission` 检查 Build、BuildLine、Part、StockItem 的查看权限，读取任务时再次检查，并按 owner 过滤。采购页面自身另外要求 `purchase_order.view`；隔离非超级用户同时拥有 `build.view` 和 `purchase_order.view` 即可在页面操作，且没有 `PurchaseOrder.add` 权限。[联调记录](milestone2_integration_validation.md)有 HTTP 与浏览器证据。

**面试讲法。** “我用宿主 Build 上下文取库存，先按 Part 汇总需求再扣一次共享库存。测试生产单两行需求 4 和 6、源库位库存 5，页面得到初步缺口 5；若把两行的库存相加会算错。我还分别验证了插件 API 权限和宿主采购页面权限。”
