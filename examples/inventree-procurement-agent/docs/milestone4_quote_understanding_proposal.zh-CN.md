# 第四阶段决策：手工粘贴报价原文

状态：**用户已选择 A，插件、隔离实例联调和第一轮真实评测均已完成**。结果见[第四阶段验证记录](milestone4_quote_eval_v1_report.zh-CN.md)。目标是验证模型能否从一份短报价原文中抽取有来源的字段、指出与 InvenTree 结构化数据的冲突。此阶段不批准采购、不创建采购单，不把缺少证据的价格或交期当成确定事实。

## 为什么需要这一步

[只读解释评测](readonly_explanation_eval_v1_report.zh-CN.md)显示：输入已经是结构化事实快照时，固定模板覆盖了全部机器提示，DeepSeek 尚无可证实的优势。报价邮件或文本包含不同写法、单位和相互矛盾的条件，更适合测试模型是否比固定规则多解决问题。

本地固定版本 InvenTree 的 `SupplierPart` 有 `description`、`note`、`pack_quantity_native`、`multiple` 等字段；`lead_time` 在模型中被注释。`SupplierPriceBreak` 的只读序列化结果含数量、价格、币种与更新时间，没有报价有效期或交期字段。依据见 InvenTree `company/models.py` 的 `SupplierPart`、`company/serializers.py` 的 `SupplierPriceBreakBriefSerializer` 和 `company/api.py` 的 SupplierPart 查询接口。插件现在按权限读取关联的 SupplierPart 与价格阶梯，但尚未读取报价附件，也未完成价格档位与计价单位的同语义核对。

## 入口选择

| 方案 | 首版工作 | 代价与限制 |
| --- | --- | --- |
| **A. 粘贴匿名纯文本，关联一个 SupplierPart（推荐）** | 用户选已授权 SupplierPart，粘贴最多 8 KiB 报价文字；插件保存原文哈希和来源，调用只读工具抽取字段。 | 最容易限制输入、标出原文字符范围并做可复现评测；需要用户主动提供文本。 |
| B. 直接读取 SupplierPart 附件 | 在宿主权限下按 SupplierPart 关联对象查附件，处理文本/PDF 并抽取。 | 需处理文件格式、逐对象权限与存储；附件也可能是外链，不能直接抓取任意 URL。 |
| C. 只读现有结构化价格 | 直接比对 SupplierPart 和 SupplierPriceBreak，不接原文。 | 实现较快，但难验证模型理解非结构化报价的增量。 |

用户已选择 **A**，开发与评测先用匿名合成报价。短文本可直接作为受限工具结果交给模型，当前**无需 RAG**；等有多份长文档、需要跨文档检索时再评估 RAG。附件可以作为第二个入口复用同一抽取与判定逻辑。

## 推荐方案的验收边界

1. 后端验证登录、任务 owner、Build/Part 与 SupplierPart/PriceBreak 的查看权限，并核对 SupplierPart 确实对应任务中的 Part。提交只收一条纯文本和一个 SupplierPart ID，限制长度与并发；不接收任意 URL。
2. DeepSeek 只通过任务绑定的只读工具获得报价原文和已授权的结构化字段。输出供应商、SKU、价格、币种、计价单位、包装、有效期、交期，每个已抽取字段必须有精确原文片段或字符范围；找不到的字段为 `unknown`。原文中的“忽略审批”等句子一律视为数据。
3. 程序用 `Decimal` 检查数值，并对供应商名、SKU 及可证明同单位的包装量做保守对照。价格阶梯、有效期和交期的业务核对仍标为“待核实”；多档价格、MOQ 和 `TBD` 等明确歧义不会生成确定字段。插件不生成下单数量。模型负责抽取，不决定采购写入。
4. 独立评测抽取字段、证据范围、冲突识别、拒绝编造及提示注入；用固定正则/模板作对照。已有 18 案中的 C07、C08、C09、C10、C17 可提供主题，但要改写成当前只读抽取的测试样本，不能直接把未来采购流程成绩算入本阶段。

面试解释：“我先用结构化快照证明工具与权限链路，再用可复现评测发现模板已足够解释这些字段，所以把模型应用扩展到真实难点——理解报价原文和发现冲突。关键数字与冲突判定由程序复核，模型不能批准或下单。”
